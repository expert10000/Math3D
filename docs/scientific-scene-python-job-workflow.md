# SSR-06 — opt-in external Python publication workflow

**Reference workflow status:** complete for a pinned, bounded, 2D scalar publication through desktop and an unpacked Windows package. The separately offered custom-script path remains trusted, unsandboxed code and is not covered by a hard OS memory/process-tree guarantee.

This workflow is for a user who deliberately wants Math3D to ask an independently managed Python environment to turn a local JSON field specification into a `scientific-scene/v1` bundle. It ships a small publisher source file, but does **not** make Python an import dependency, evaluate a scene file, bundle an interpreter for this path, or connect to Theory Lab's worker. The existing read-only `.sscene` and `.qscene` paths remain usable without Python.

1. In the desktop scientific examples dialog, choose **Publish with reference Python script…**. Electron—not renderer JavaScript—opens native pickers for an independently managed absolute Python 3.10+ executable, the JSON spec, and a new `.sscene` output path. The spec picker points to a shipped 5×5 `sin(x)cos(y)` example for a first run. The reference `.py` script is shipped as a small, pinned source asset; it is **not** a bundled interpreter. **Publish with custom Python script…** additionally asks for a trusted local `.py` file. Nothing runs yet.
2. Math3D checks file types and size limits, hashes the script and spec, and shows the selected paths and hashes. The user explicitly confirms execution of that local code. Changing a selection requires preparing again.
3. A `scientific.publish-python` operation enters the existing revision-safe `ScientificJobService`. Its source guard identifies this prepared script/spec pair; the renderer sends only an opaque session and job ID through the narrow preload API. The main process re-hashes both files immediately before starting and after the process exits.
4. Electron starts the selected Python executable with isolated mode and fixed arguments: `-I <selected-script> --spec <selected-spec> --output <private-temporary-bundle>`. There is no shell, URL, arbitrary argument field, import-triggered execution, automatic retry or idle Python process. The app enforces one job per window, bounded diagnostics and a deadline. Cancel and window close terminate the Windows process tree or POSIX process group where possible.
5. After successful exit, the existing main-process `scientific-scene/v1` reader checks the temporary bundle's envelope, version, paths, bounds, links, metadata, finite values and SHA-256 hashes. The supported 2D scalar display is derived only after verification. The spec/script hashes are checked again; only then is an absent destination exclusively created. A temporary incomplete marker makes partially moved files fail closed; the marker is removed only after all files arrive. A successful job may open the result read-only.
6. Cancel, timeout, source change, bad output and process failure attach no **new** scene or successful job result. A private job-owned temporary directory is cleaned up. The user-selected output is never overwritten. Python's code and source claims are **user-trusted/supplied**, not authenticated by the scene hashes.

The first adapter intentionally uses the standalone publisher's fixed CLI. Its generic `scientific-scene/v1` output may describe 2D scalar, 3D scalar or 3D complex fields, but the current generic Math3D preview supports only bounded 2D scalar height surfaces. Broader generic views, Python environment management, Jupyter, remote execution and background services remain separate decisions.

This is a supervised **trusted local-code** workflow, not a sandbox. The reference script is pinned and bounds input count, shape and binary output; the spec, script, diagnostics, scene payload and elapsed time are bounded by Math3D. The existing job service records a cooperative memory reservation. Cancellation targets ordinary descendants, but arbitrary custom code may detach children and there is no hard OS resident-memory or descendant-process limit. Hard isolation for custom scripts remains a separate future gate, not a claim of this completed reference workflow.

## Desktop UI steps

1. Open **File → Verified quantum examples** and choose **Publish with reference Python script…** under **Scientific interchange proof**.
2. Pick your installed `python.exe` (Python 3.10 or newer). In the JSON picker, use the offered `sincos-grid.json` example for a first run, or choose your own bounded scientific field specification.
3. Choose a **new** destination ending in `.sscene`. Review the script/spec paths and SHA-256 hashes in the dialog. No process has started yet.
4. Click **Run trusted Python publisher**, then approve the native **Run external Python code?** confirmation. Cancel is available while the job is active.
5. Math3D verifies and previews the 2D scalar scene. Inspect a sample; later, reopen the saved directory with **Open external .sscene folder…**. This also works after restart. Changed source bytes are refused.

The custom-script button asks for an additional `.py` path. Use it only for code you trust; it is not the pinned reference path. Importing an existing `.sscene` never launches Python.

On the 2026-10-13 Windows development build, the existing footprint scripts measured 865,080 B gzip for the renderer entry and 2,390,777 B gzip for all JavaScript after the completed reference UI. The preceding local idle measurement had median shell-ready time 1,070 ms, working set 569,928 KiB and four Electron processes. These are local regression observations, not guarantees; there was no idle Python process. The isolated runner acceptance covers success, the shipped example, source changes before and during execution, ordinary Windows descendant cancellation, timeout, diagnostic overflow and cleanup. Electron acceptance covers reference and custom preparation, native refusal, success, cancel, restart/tamper refusal and the older read-only import path. `npm run build:core`, `npm run package:ssr:probe` and `npm run test:ssr:package` verified an unpacked Windows app: the shipped script hash, sample JSON, external Python publication and visible UI entry. The package probe omits unrelated worker/web resources and does **not** assert that the full installer passed its separate release gates.
