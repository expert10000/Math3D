# Scientific capability and platform discovery

Math3D now separates five scientific concepts:

| Concept | Contract | Meaning |
| --- | --- | --- |
| Capability | `ScientificCapability` | Mathematical work a module intends to offer. |
| Operation | `ScientificOperation` and `ScientificOperationDescriptor` | A versioned implementation and its discoverable input, parameter, and output contract. |
| Result | `ScientificResult` | One execution against a source reference. |
| Metric | `ScientificMetric` | A measured value from that result. |
| Artifact | `ScientificArtifact` | A retained output reference. |

The common capability registry in `packages/core/src/scientificCapabilityRegistry.ts` covers Graph 2D, Graph 3D, Curve, Surface, Mesh, Geometry, Volume, Topology, CAS, Number Theory, Complex Analysis, Field Explorer, and Quantum. Entries with `status: "catalogued"` are discovery and roadmap entries. They have no claimed executable operation. Consumers must check the host environment and implementation availability through `runnableFor` before offering execution.

The first fully described operation is `surface.curvature.compute`. It implements Gaussian, mean, and principal curvature capabilities from the same sampled input and describes the histogram parameter, field and statistics outputs, numerical method, validation, and execution properties. The Surface UI and Surface Analysis worker both call the same bound implementation in `renderer/src/surfaceAnalysis/surfaceCurvatureOperation.ts`. The existing Surface result store still owns result retention, source freshness, and cache behavior. `surface.curvature.analytic-reference` samples exact derivative presets on a bounded grid, and `compareSurfaceCurvatureReference` checks a corresponding candidate field with explicit units, grid, coverage and tolerance checks. `mesh.normals.compute` is also fully described and all callers of `computeVertexNormals` use its registered binding. Other canonical worker entries retain partial schemas until checked against their implementations and tests.

`packages/core/src/platformDiscovery.ts` adds a common `list`, `get`, `related`, and `executableOperation` interface for scientific operations, mathematical objects, computational methods, features, visualizations, UI routes, commands, metrics, validators, workflows, journeys, runtime providers, and exporters. References are checked when the service is created. A registered operation must agree with its capability registry entry.

Fifteen descriptors now have `schemaCompleteness: "complete"`: sampled Surface curvature, serializable parametric Surface curvature, analytic Surface curvature reference, Mesh vertex normals, and one bounded reference operation for each of the other 11 modules. The new operations cover quadratic real roots, a 3D quadratic gradient, polyline arc length, Euclidean distance, trilinear interpolation, triangle mesh Euler characteristic, integer polynomial differentiation, modular inverse, real quadratic complex zeros, affine field divergence, and sampled wavefunction probability density. They accept the specific bounded inputs in their contracts; they do not implement the full proposed capability list for any module. Their JSON compatible input, parameter, and output values pass contract validation against real results. The retained sampled Surface result is adapted to stable capability, metric, and artifact identifiers only after source identity, revision, representation, units, and sample bounds agree. Other canonical worker descriptors have `schemaCompleteness: "partial"`; they cannot generate parameter editors, workflow nodes, benchmarks or SDK calls. An incomplete descriptor is not advertised as available by the discovery adapters even if a backend implementation ID is reported.

The next complete descriptor is `surface.curvature.parametric`. It accepts a JSON serializable `ParametricSurface` definition with x/y/z expressions and a bounded u/v domain, defaults to a 128×128 grid, and uses the existing adaptive numerical differential engine. Its output includes the curvature field, domain coverage, finite value status and a reference comparison status. If the caller names an exact preset whose formula, domain, units and orientation match the submitted definition, the operation automatically computes the independent analytic reference and compares K, H, k1 and k2 on the same grid. Without such a reference, the status is explicitly `unavailable`; it does not claim an analytic check of arbitrary expressions. The Capabilities panel exposes an editor and a Gaussian field preview, with computation in a browser worker. The existing `surface.curvature.compute` remains the lower level operation over already sampled curvature arrays.

`packages/core/src/scientificOperationProducts.ts` derives parameter metadata, workflow node templates, Markdown contract documentation, a metric checked result inspection model, and a schema checked benchmark runner from complete descriptors. Generated nodes and benchmarks require an explicit verified host binding. Surface result adaptation checks metric identifiers against the same registry before presenting retained evidence. The API client exposes descriptor generated documentation and server eligible workflow nodes.

`packages/core/src/scientificWorkflow.ts` executes a bounded sequence of verified operation nodes. A node can reference an earlier output by ID and path; input and output schemas are checked at each step. The Capabilities panel now contains a generic JSON workflow editor for complete browser bindings. The editor runs in a worker and shows each step's output. It is a functional sequential builder for registered operations, not a visual graph canvas or a replacement for the project journeys.

`services/scientific-api` exposes `GET /v1/operations`, `GET /v1/workflow-nodes`, `GET /v1/operations/:id/docs`, `POST /v1/operations/:id/execute`, and `POST /v1/workflows/execute`. The service binds all 15 complete operations to the same registered implementations used in the UI. It validates JSON requests and responses and listens on loopback by default. Build with `npm run build:scientific-api`, then run `npm run start:scientific-api`. The TypeScript API client and `integrations/python/scientific_operations.py` discover those real server bindings and call them over HTTP; neither advertises partial or unbound operations. Python `connect_scientific_api("http://127.0.0.1:8772")` also supports workflow execution.

The desktop and web module navigation has a **Capabilities** button. Its panel follows the selected module and offers a selector for all 13 scientific modules, including Graph 3D, Field Explorer, and Quantum. It separates operations verified in the current host, registered operations without a verified local binding, and planned capabilities. The available Surface curvature operation opens the existing analysis controls. The Surface computation panel and command palette also use the same descriptor. The panel does not imply that all listed mathematics can be computed.

The panel also shows a source-backed inventory of existing workspace features for each module, grouped as Create, Edit, View, Analyze, Export, and Study. Analysis entries for Curve, Surface, Mesh, and Geometry are drawn from their respective result-kind registries; exact CAS and Number Theory entries come from the algebra operation registry; Graph tools and Field derived operations likewise come from their module definitions. Other workspace entries describe existing authoring, visualization, and export controls. A workspace entry is a navigation aid, not a claim that an operation can execute on every source or host. Graph 3D currently has no dedicated workspace; its capability entries remain registered or planned according to their actual status.

Host discovery requires an explicit implementation binding. Desktop and web bind sampled and parametric Surface curvature, Mesh normals, and the 11 bounded module operations. The loopback scientific API binds those plus the analytic Surface reference; the generic API adapter advertises none without a server binding report. Mobile advertises none by default. Python discovery reads descriptors plus the server's verified binding report and returns none without it. An operation's environment declaration alone is insufficient.

## Integration progress and next work

1. **One per module complete:** Every scientific module has at least one complete, tested operation. Finish the other proposed capabilities one at a time; most catalogued entries are still future work.
2. **Retained evidence:** Sampled curvature, serializable parametric curvature, analytic reference sampling, Mesh normals, and the 11 module reference operations have validated execution contracts. Extend retained result, metric and artifact adapters beyond sampled Surface curvature.
3. **Generated contracts available:** Parameter metadata, workflow nodes, API Markdown and benchmark execution consume complete descriptors. A sequential JSON workflow editor runs in the application. A visual graph editor, saved workflow documents, generic parameter form widgets and a generic retained result inspector remain future work.
4. **Guarded across hosts:** The loopback server, TypeScript API client and Python transport execute 15 verified operations. Mobile bindings and static Python SDK methods remain future work. Expanding server execution requires a complete schema and a tested handler for each operation.
