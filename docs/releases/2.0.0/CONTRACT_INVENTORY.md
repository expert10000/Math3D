## Overlap and decisions needed for M3D20-01b–d

1. **Project-like envelopes are not interchangeable.** `Math3DProject` is the named aggregate; `MixedWorkspaceDocument` is its document/result collection; `SceneProjectDocument` is legacy scene persistence; the two handoffs are transport formats. A new 2.0 Study or `Open in…` operation should extend the Project/workspace contract, not introduce another owning Project ID. Keep legacy readers and explicit migrations.
2. **There are two result layers.** `AnalysisResultEnvelope` is the versioned saved workspace evidence. `renderer/src/analysis/contracts.ts` and `renderer/src/analysis/resultStore.ts` provide active Mesh analysis state through `renderer/src/mesh/analysisResultStore.ts`. The latter can carry progress/payload and is not the saved Project result registry. M3D20-01b must define an adapter and publication boundary before a common Result Card treats them alike.
3. **There are three selection lifetimes.** `UnifiedSelection` is Geometry/Mesh UI interaction; `ViewerCommittedSelection` is a saved set of source-linked entity IDs; `ScientificSelection` is a Project-owned typed mathematical selection. The proposed Scientific Cursor should coordinate qualified mappings among these, preserve their distinct lifetimes, and refuse stale or incompatible frames.
4. **Capability information has several levels.** `PlatformCapabilitySnapshot` describes host facilities, `MATH3D_WORKER_OPERATION_REGISTRY` describes worker operations, and documents/handoffs declare required capabilities. M3D20-01b needs a qualified cross-module adapter registry that uses these existing facts and explicit disabled reasons. None alone proves that a user journey is supported on a given host.
5. **Artifact metadata and bytes have separate owners.** Workspace results refer to artifact handles/manifests; the Project package verifies source sidecars; the kernel resource store manages runtime bytes. A new adapter must preserve the exact source/resource hash and cannot mark a result verified merely because a handle exists.
6. **External scene references overlap in purpose.** Project scene references pin folder/fingerprint, while the workspace scientific scene catalog records discoverable dataset metadata and quantum/field documents are read-only views. The 2.0 Study design must identify which existing reference it stores and how missing or moved source bytes are reported, without copying external assets into Study ownership.
7. **`QuantumStudyDocument` is an existing narrow Study.** General `StudyDocument` must define a migration or coexistence rule for this format before implementation. Renaming it or treating its panels as a general schema would risk existing Project reopen behavior.

## Contract rules to carry into the freeze

- Keep one Project identity and one workspace source for persisted document/result relationships. Do not infer lineage from titles, UI proximity, or matching coordinates.
- Preserve exact document revision/hash and resource identity across derivation, result publication, save/reopen, and export. A Project aggregate revision is not a substitute for a source generation.
- Validate every module checkpoint and replay against the expected identity; a missing adapter or divergent replay is an error, not a regenerated document.
- Keep result authority (`exact`, `certified`, `numerical`, etc.) separate from availability/freshness (`current`, `stale`, `missing`, etc.). A UI card must show both without promoting one into the other.
- Link coordinates only with a declared frame, unit, and versioned mapping; unmatched domains remain usable locally with a stated reason for disabled linking.
- Treat legacy scene projects, handoffs, unversioned results, and legacy selection slots as explicit compatibility inputs. Do not silently upgrade their evidence status.
- Keep source resources and external scene bytes under their present owners. Study layouts, result cards, and handoffs reference them and report missing or changed bytes.
