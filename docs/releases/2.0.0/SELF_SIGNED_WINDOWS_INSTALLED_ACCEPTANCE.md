## Run on two clean Windows snapshots

Use two separate fresh Windows 10/11 VMs or disposable Windows runners, one for `Fresh` and one for `Upgrade`. Each must begin without a Math3D uninstall entry in HKCU or either HKLM uninstall view; the runner refuses any existing entry before starting an installer. Do not run it on the local host, which has stable Math3D 1.4.9 registered. Use a dedicated VM user profile and a new evidence directory below that VM's `%TEMP%` for each mode.

For the final candidate, first freeze the merged source commit and build a new signed installer from it. Supply that commit, installer SHA-256, and signer thumbprint as required, independently reviewed runner arguments; the harness does not hardcode candidate-specific values or need a post-freeze source edit. The table above identifies only the provisional PR #114 example package. Provision two clean Windows 10/11 snapshots with 8 GiB or more RAM, a writable temporary disk, and a file-transfer path for the installer, public manifests, published 1.7 installer, and harness checkout. Transfer no private signing key. Run `Fresh` on one snapshot and `Upgrade` on the other; retain both evidence directories outside the disposable VMs. Budget roughly 1-2 hours per snapshot for provisioning, dependency transfer, installation, desktop tests, and receipt review. This is a planning estimate, not a measured test duration.

Install PowerShell 7, Node 24 and 7-Zip in the VM, clone this review branch, and run `npm ci` in the checkout. Stage the exact candidate package and public manifests in one VM folder. Stage the exact published 1.7 installer together with its release `candidate-manifest.json` and `SHA256SUMS.txt` in another folder for `Upgrade`. Run these commands in `pwsh`:

```powershell
$repo = 'C:\qualification\Math3D'
$candidate = 'C:\qualification\candidate'
$old = 'C:\qualification\published-1.7\Math3D-Setup-1.7.0.exe'
$source = '<approved 40-character final source commit>'
$installerSha256 = '<approved 64-character installer SHA-256>'
$signerThumbprint = '<approved 40-character signer thumbprint>'
& "$repo\scripts\release20-selfsigned-installed.ps1" -Mode Fresh -ArtifactRoot $candidate -EvidenceRoot "$env:TEMP\math3d-selfsigned-fresh" -SourceCommit $source -InstallerSha256 $installerSha256 -SignerThumbprint $signerThumbprint
# Revert to a clean VM snapshot before running the second mode.
& "$repo\scripts\release20-selfsigned-installed.ps1" -Mode Upgrade -ArtifactRoot $candidate -OldInstaller $old -EvidenceRoot "$env:TEMP\math3d-selfsigned-upgrade" -SourceCommit $source -InstallerSha256 $installerSha256 -SignerThumbprint $signerThumbprint
```

If a Sandbox mapped checkout cannot access Git metadata, pass its reviewed 40-character PR head with `-HarnessCommit` in both commands. The receipt then records that commit and the runner script SHA-256; ancestry must be checked in the host checkout before launching the Sandbox. A normal clone checks ancestry itself.

When a stable SageMath 10.10 HTTPS endpoint is available from the VM, supply it through the process environment variable `MATH3D_RELEASE20_SAGE_SERVICE_URL`, sourced from a CI secret or equivalent VM secret store. The runner never writes that URL to its receipt. It requires the endpoint's `/health` source commit to match the installed candidate, then runs the live ideal and polynomial cusp/smooth oracle, all five test specs that cover the four advertised journeys, and their exact Playwright receipt. Without the variable it records the Sage journeys as blocked and marks the fresh receipt `partial`. Do not put the URL or any path token on a command line or commit it to the repository.

The runner verifies the fixed installer SHA-256, freeze receipt, signer, timestamp, current self-signed code-signing chain, and pinned NSIS component before installation. It verifies installed `Math3D.exe` and frozen `worker.exe` hashes and signatures. `Fresh` runs the frozen worker protocol smoke and first-use tests with Python and Conda removed from `PATH`, Project cold reopen, hard-exit Project/sidecar recovery, Volume context-loss and cancellation, four-pane Study restart, and the installed worker loss/reconnect/retry driver with isolated Project sidecars. The nonmemory test receipt uses `build-identity.json` extracted from the installed `app.asar` and verifies its source commit. `Upgrade` installs the published 1.7 asset, seeds and cold-reopens a real Graph Project and disabled setting, backs up and inventories its profile, installs 2.0 into the same directory, and checks retained bytes and setting. For rollback it verifies the installed 2.0 registration and signed uninstaller, makes a hash-identical temporary copy, then runs the normal silent uninstall with `/KEEP_APP_DATA` and the exact install directory. It waits for the 2.0 registration and executable to disappear, checks that uninstall preserved the active profile and the pristine 1.7 backup and clone, installs the exact published 1.7 asset into the same directory, and reopens the exact original Project bytes from the clone. Directly running the old 1.7 installer over registered 2.0 is not the qualified rollback procedure.
