# M3D20-13 installation and upgrade gates

These gates are for the **exact signed 2.0.0 candidate**, not a source checkout or a renamed 1.7 installer. The source version is now aligned to 2.0.0, but the installer and upgrade gates remain pending until a signed candidate manifest and artifacts exist.

The manual [2.0 candidate workflow](../../../.github/workflows/release20-candidate.yml) and `scripts/build-release20-candidate.ps1` stop before packaging unless root, renderer and both npm locks identify a clean reviewed 2.0.0 commit and the Windows signing inputs are present. The workflow also imports the PFX in ephemeral memory and checks its private key, code-signing usage, validity period, approved thumbprint, and timestamp URL before installing build dependencies. The builder freezes the worker, checks its protocol, verifies Authenticode on the installer/app/worker, extracts the exact NSIS 3.13 `System.dll`, and writes a candidate manifest, signatures, SBOM, attributions and asset checksums under one temporary output. This is a build route, not an installed receipt. The repository currently has no `MATH3D_WINDOWS_CSC_LINK`, `MATH3D_WINDOWS_CSC_KEY_PASSWORD`, or `MATH3D_WINDOWS_SIGNER_THUMBPRINT` secrets and no `MATH3D_WINDOWS_TIMESTAMP_URL` variable; this host has no code-signing certificate. A signed 2.0 installer cannot yet be built.

The [Windows Installer Smoke workflow](../../../.github/workflows/windows-release-smoke.yml) is source-only: it builds and installs an unsigned **Math3D Dev** package from the checkout, then runs worker and packaged UI smoke. Its `release-dev` artifact is never a 2.0 candidate. The stable 2.0 package remains on the signed candidate route above, which fails closed without valid signing inputs.

The [exact-candidate qualification workflow](../../../.github/workflows/release20-qualification.yml) takes the candidate build run ID, reviewed source commit, approved installer SHA-256, and approved freeze SHA-256. It downloads that run's immutable artifact, checks the complete uploaded checksum set and candidate/source/SBOM identities, then uses separate clean Windows 2022 runners for fresh installation and the pinned published 1.7 upgrade/rollback. The final receipt passes only when all three records identify the same installer and signer and every installed check passed. `scripts/verify-release20-uploaded-assets.mjs` verifies portable artifact contents; the installed runners independently check Authenticode and installed app/worker bytes. This route has not run: no valid code-signing identity or signed 2.0 candidate was found in the repository configuration or local certificate stores.

## QI-40 installer status carried into 2.0 (2026-11-07)

The [currently published v1.7.0 Math3D installer](https://github.com/expert10000/Math3D/releases/download/v1.7.0/Math3D-Setup-1.7.0.exe), SHA-256 `eacffc903e988a15636f556b36d12621b9918f4cec69e5c8b19e7daa512222db`, still embeds the 12,288-byte NSIS `System.dll`, SHA-256 `3eb38ae99653a7dbc724132ee240f6e5c4af4bfe7c01d31d23faf373f9f2eaca`. Intermittent `0xC0000005` installer crashes were reproduced in that shared component on old-toolchain Math3D and TheoryLab candidates. The component identity is established; the precise access-violation call site is not.

The [NSIS 3.13 production fix](https://github.com/expert10000/Math3D/pull/29) is on `main`, but it has not replaced the published download. Its final [nonpublishing two-app signoff](https://github.com/expert10000/Math3D/actions/runs/42396101411) built Math3D SHA-256 `1518115d4891701a53407a0e73a5a4b892b4d7e9d8a510e9388da30cb0afc3a2` and TheoryLab SHA-256 `377707a7c917a5f1aabf7bc8cdc89f7ab44343800219bf6f562140664f815d25`. Both embed the pinned 30,208-byte `System.dll`, SHA-256 `1556ee1bf1cb477124e1269b534ed81653ba71994dab7903ee3782b75acc2810`. The exact files passed [18/18 install attempts on Windows 2022](https://github.com/expert10000/Math3D/actions/runs/42397460986) and [18/18 on Windows latest](https://github.com/expert10000/Math3D/actions/runs/42397463035), covering Math3D-only, TheoryLab-only, and both-app installs. Installed UI/QEC, saved-profile rollback, and v1.6.0 upgrade passed on the same Math3D hash. See the [exact evidence report](https://github.com/expert10000/Math3D/blob/c83583a458a3566f82ac025c0e3471f93e3b8b7a/docs/evidence/quantum-qi40-nsis313-production-2026-11-07.md).

This evidence supports the installer toolchain change, but **does not certify a 2.0 installer**. The 2.0 GA path is separate from the guarded legacy 1.x release workflow. Carry the pinned toolchain and embedded-DLL assertion into the actual 2.0 packaging path, then repeat clean installs, first launch, upgrade, rollback, and final downloaded-byte checks against one signed 2.0 candidate. Preserve any crash from the pinned old 1.7 installer as a separate baseline failure rather than attributing it to 2.0; the old rollback installer also reproduced this crash in the 1.7-line test.

QI-40 memory signoff remains open. An [installed current-main 80-cycle run](https://github.com/expert10000/Math3D/actions/runs/42392998992) measured 2,832,516 bytes of late forced-GC heap growth against the provisional 2,097,152-byte target. That run used an earlier candidate, so it is neither a pass nor an exact memory measurement for the final installer above. An installed memory result within budget, tied to the actual 2.0 candidate hash, is required before 2.0 release signoff.

## Fresh Windows installation (13b)

On a clean Windows VM, use `scripts/release20-fresh-install.ps1 -InstallerPath <exact installer> -CandidateManifest <manifest>`. The runner requires the manifest's exact installer bytes, signer thumbprint, app and worker hashes, and pinned embedded NSIS component before installation. It refuses an existing stable Math3D registration or install directory, checks installed app and worker bytes and signatures, checks bundled web resources, runs worker protocol smoke with Python/Conda removed from `PATH`, then launches the installed app with an isolated profile. Its UI test opens the built-in Minimal Surface Study, checks Graph/Curve/Surface documents, saved derivative evidence, lineage and Notes, closes the app, and reopens the exact Project from its library. A JSON evidence file records each passed check and the installer identity. Failure leaves the installation for investigation; the runner does not remove pre-existing user files.

The same first-use UI test can run against the source build with `npx playwright test tests/e2e/release20-first-use-study.spec.ts --reporter=list`. That check is useful while developing the gate but does not count as installed-candidate signoff.

## Upgrade (13c)

On a clean Windows VM, download the [published v1.7.0 installer](https://github.com/expert10000/Math3D/releases/download/v1.7.0/Math3D-Setup-1.7.0.exe) and run `scripts/release20-upgrade.ps1 -OldInstaller <Math3D-Setup-1.7.0.exe> -CandidateInstaller <Math3D-Setup-2.0.0.exe> -CandidateManifest <manifest>`. The runner accepts the old installer only when its SHA-256 is `eacffc903e988a15636f556b36d12621b9918f4cec69e5c8b19e7daa512222db`. It verifies the exact signed stable 2.0.0 candidate against the manifest before installing either app.

The 1.7 phase creates a Graph Project using the published app's My Graphs interface and disables command preview overlays. It records the exact saved Graph workspace bytes and a SHA-256 digest. The runner inventories every original profile file, checks a byte-identical backup, installs the exact signed 2.0 app and worker over the same application directory, then launches 2.0 against the original profile. The 2.0 phase checks the setting, compares the original Graph workspace bytes, and reopens the saved Project through My Graphs. It rechecks the untouched backup, clones that backup to a separate rollback profile, reinstalls 1.7, and reopens the original Graph bytes there. JSON evidence records both versions, hashes, phase results, backup path, and any failure. Failure leaves the work root and backup in place for inspection. A skipped UI test cannot pass because the runner requires each phase's evidence file. The published 1.7 installer may itself fail because of QI-40; this is reported as a baseline or rollback failure, never a 2.0 pass.

This gate is ready to execute but remains **pending** an exact signed 2.0.0 candidate. It does not claim that a 1.7 Graph Project has already survived a 2.0 upgrade.

## Evidence rule

Record the candidate commit, installer hash and signature, old installer hash for upgrades, and separate results for byte identity, install, worker, UI, data preservation and backup. A missing artifact or skipped test cannot be reported as passed.
