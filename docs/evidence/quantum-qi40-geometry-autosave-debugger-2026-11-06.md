# QI-40 Geometry restore, autosave ablation, and installer stack readiness · 2026-11-06

This follows the [Graph rollback and heap budget report](quantum-qi40-graph-heap-installer-components-2026-11-06.md). The QI-40 release freeze is still open.

## 1. Promoted Geometry restore limit

The prior installed rollback found that a saved Project with promoted QWZ Geometry opens only as a compatibility preview in the pinned pre-QEC app. The current app has the same native Geometry editor limitation for scene primitives: `geometryEditorSeed` refuses `source.geometry`. A unit regression now asserts the exact compatibility reason for such a saved Project, and the [QI-21 promotion E2E](../../tests/e2e/quantum-qi21-native-promotion.spec.ts) saves, reloads, and confirms the preview reason in the UI. The promotion message now states this limit before the user saves. The source scene and promoted document remain preserved, but no editable Geometry rollback claim is made. A separate editor adapter or explicit migration is needed to close the gap.

## 2. Workbook autosave contribution to heap growth

The stress harness now supports a disposable-profile ablation that suppresses only the two workbook autosave `localStorage` writes. Both modes clear those keys and reload before the baseline; they still build workbook payloads and run the same alternating 80 Rice–Mele/hydrogen scene cycles. In the matched local pair, the [control](quantum-qi40-matched-autosave-control-local-budget-2026-11-06.json) grew **10,917,708 bytes** between closed cycles 20 and 80, and the [ablation](quantum-qi40-matched-autosave-ablation-local-budget-2026-11-06.json) grew **9,810,588 bytes**. The **1,107,120-byte difference** is much smaller than the first, confounded comparison that reloaded only the ablation. Control storage ended with 92,409 current-session bytes and 184,730 journal bytes; the ablation asserted zero for both. String self-size growth fell from **16,319,524** to **13,035,000 bytes**, but both total heap slopes missed the provisional 2 MiB target. The [control samples](quantum-qi40-matched-autosave-control-local-80-2026-11-06.json) and [ablation samples](quantum-qi40-matched-autosave-ablation-local-80-2026-11-06.json) retain all per-cycle measurements.

The [fresh Windows matched run](https://github.com/expert10000/Math3D/actions/runs/42222485923) reversed the small local difference: [control](quantum-qi40-matched-autosave-control-windows-budget-2026-11-06.json) growth was **9,754,248 bytes**, and [ablation](quantum-qi40-matched-autosave-ablation-windows-budget-2026-11-06.json) growth was **10,906,780 bytes**. Control storage held 92,393 current-session and 184,714 journal bytes; ablation storage was zero. Both runs held WebGL contexts at 1 → 1, textures at 5 → 5, with no canvas mismatch. Each final snapshot retained **36 large strings** totaling about **17.03 MB** of shallow string bytes, with the same top workbook JSON prefix group (17 strings, about 8.28 MB). The [control](quantum-qi40-matched-autosave-control-windows-80-2026-11-06.json) and [ablation](quantum-qi40-matched-autosave-ablation-windows-80-2026-11-06.json) samples show the full cycle series. Thus autosave writes are not a reproducible dominant cause of the heap slope; the workbook-shaped strings need a different retainer explanation, and the provisional budget remains failed.

## 3. Installer crash stack readiness

The installer probe already enables per-application WER mini dumps and records a dump hash without uploading process memory. It now detects the Windows CDB debugger. If an installer crashes and a dump appears, it runs `.exr -1; .ecxr; k` against that dump and stores only the exception code and up to 20 module/function frame labels; raw dump and debugger output remain on the ephemeral runner. Microsoft documents [CDB dump opening](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/analyzing-a-user-mode-dump-file) and the [`.ecxr` exception context](https://learn.microsoft.com/en-us/windows-hardware/drivers/debuggercmds/-ecxr--display-exception-context-record-).

The [first 12-probe matrix](https://github.com/expert10000/Math3D/actions/runs/42222131178) passed eleven installs and reproduced the Math3D `0xC0000005` crash once. Its [sanitized report](quantum-qi40-installer-crash-cdb-first-42222131178.json) confirms CDB is available, a 2,859,998-byte WER mini dump was captured, and CDB read exception `c0000005`; Application Error 1000 again names `System.dll` at offset `00001581`. The first extraction used `kb`, whose argument columns did not match the narrow frame parser, so it yielded no frame labels. The probe then switched to `k` and recorded stack-like line count. The [second matrix](https://github.com/expert10000/Math3D/actions/runs/42222777457) reproduced a Theory Lab `0xC0000005` crash; its [sanitized report](quantum-qi40-installer-crash-cdb-second-42222777457.json) again has CDB exception `c0000005` and Windows `System.dll` offset `00001581`, but **zero stack-like lines**.

The [third matrix](https://github.com/expert10000/Math3D/actions/runs/42223452764) reproduced a Theory Lab crash at the same module offset. Its [bounded CDB diagnostics](quantum-qi40-installer-crash-cdb-third-42223452764.json) show that the debugger executed the exception and stack commands, then found symbol tokens `System!Store+0x4a0`, `System!Call+0x7f`, and installer frames. The `System!Store` symbol narrows the fault location beyond the DLL name. [NSIS System plug-in documentation](https://nsis.sourceforge.io/Docs/System/System.html) describes `Store` as performing stack/register operations. CDB also reported a stack-unwind warning and no parsed frame lines, so these tokens are **candidates**, not a verified ordered call stack. The trigger and the exact caller input remain unresolved; this evidence points the next reproduction toward `Store` argument/state inspection or a stronger dump type.

QI-40 remains open for an editable Geometry restore path, the remaining non-autosave heap growth, installed-build memory certification, and a diagnosed installer crash.
