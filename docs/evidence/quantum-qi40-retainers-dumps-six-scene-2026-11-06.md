# QI-40 retained paths, installer dumps, six-scene rollback · 2026-11-06

The [Windows workflow](https://github.com/expert10000/Math3D/actions/runs/42208082996) passed all eight jobs using the archived candidate Math3D and Theory Lab installer bytes pinned in the [earlier installed report](quantum-qi40-rollback-stress-installer-2026-11-06.md). The rollback job also installed the pinned pre-QEC 1.7.0 Math3D package. Results apply to those exact binaries, not later `main` builds.

## 1. Retained-object paths after installed scene close

The [40-cycle installed report](quantum-qi40-installed-retainer-paths-40-2026-11-06.json) alternated Rice–Mele bands and hydrogen 2p density surfaces. Every close returned to the baseline canvas count and simulated WebGL context loss was observed. Forced-GC renderer heap rose from 29,609,292 to 37,357,676 bytes. V8 snapshot counts rose from 2 to 42 `WebGL2RenderingContext` wrappers and included 200 more `WebGLTexture` wrappers; string nodes gained 7,601,440 shallow bytes. All six sampled targets had a path to a GC root. Three context paths included `HTMLDocument` → event listener → bound control object → `domElement` → WebGL context. This identifies a retaining route in the archived renderer, but the sampled shortest paths do not prove it is the only route or measure live GPU allocation. Current `SurfaceViewer` source calls `renderer.dispose()` and `forceContextLoss()` on close; an independent source experiment that removed OrbitControls key listeners from the original document still showed one retained context per cycle. No cleanup fix is claimed here. Three.js [documents `WebGLRenderer.dispose()` as GPU resource cleanup](https://github.com/mrdoob/three.js/blob/dev/docs/pages/WebGLRenderer.html.md), while its [older issue about shared dispose listeners](https://github.com/mrdoob/three.js/issues/20346) describes a related retention pattern. A targeted fix and post-fix installed measurement remain necessary.

## 2. Theory Lab crash dump readiness

Six fresh Windows runners installed the exact archived Theory Lab package with a per-application WER mini-dump rule enabled. All six [reports](quantum-qi40-lab-dump-probe-1-2026-11-06.json) passed; the remaining reports are [2](quantum-qi40-lab-dump-probe-2-2026-11-06.json), [3](quantum-qi40-lab-dump-probe-3-2026-11-06.json), [4](quantum-qi40-lab-dump-probe-4-2026-11-06.json), [5](quantum-qi40-lab-dump-probe-5-2026-11-06.json), and [6](quantum-qi40-lab-dump-probe-6-2026-11-06.json). Each records `configured: true` and zero dump files because no installer crashed. The runner removed its per-application registry rule after the probe. The harness follows [Microsoft's WER LocalDumps documentation](https://learn.microsoft.com/en-us/windows/win32/wer/collecting-user-mode-dumps); it uploads only dump name, byte count and hash if a future crash occurs, never raw process memory. The earlier `0xC0000005` fault remains unexplained, so installer reliability is still open.

## 3. Six-scene installed Project rollback

The [rollback report](quantum-qi40-six-scene-rollback-2026-11-06.json) passed exact installer hashes, QEC candidate install and scene open, candidate uninstall, pre-QEC install, Graph copy and setting retention, and pinned v1/v2 readers. One saved Project retained the same ID and exact fingerprints for QWZ curvature, Rice–Mele bands, ideal QEC, hydrogen 2p field, Rice–Mele pump and Kitaev bands. The older installed app reopened and actively verified all six Project references. This extends the prior three-reference check across field, time and another v2 band scene; it does not certify every Project document or newer result adapter.

QI-40 release freeze remains open for installer root-cause/reliability evidence and a post-fix memory budget, alongside the other partial gates in the certification report.
